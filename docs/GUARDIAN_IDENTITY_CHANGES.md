# Guardian identity changes

Migration 010 adds an Auth-user update trigger. An email change or removal of an existing email confirmation invalidates the family's studio verification and consent, pauses supervision, revokes parent unlock sessions, and unpublishes projects. Suspended accounts stay suspended; other accounts return to pending. Credits and projects are preserved. Restoring email confirmation does not restore approval or publication automatically. The family must verify the new email, receive a new consent/approval review, and request publication review again.

Routine sign-in timestamp changes do not invalidate approval. The trigger uses the existing safety-revision mechanism to invalidate in-flight generation and reservation snapshots. It cannot recall already displayed pages or emails already accepted by a provider. This is not a complete account recovery, deletion, or provider-session revocation workflow.

Deploy only to the dedicated Supabase project after migrations 001 through 009. No live migration was applied. Validate real Google/email change and confirmation-revocation flows with Supabase Auth, including mail queue handling and concurrent approval requests, before launch. Embedded PostgreSQL fixtures cover unrelated Auth updates, email changes, preserved credits, removed unlocks, hidden publications, confirmation revocation and suspension preservation.

Migration 011 makes administrator approval/suspension and the associated audit entry atomic. Approval requires the exact safety revision displayed when the administrator reviewed the account, a current studio email verification and a nonempty consent reference. A stale or repeated approval fails closed and requires refresh. The API still verifies the administrator before invoking this service-only procedure; the SQL actor ID is an audit identity, not an independent administrator authorization mechanism.

Approval never starts a supervised session. Suspension revokes parent unlocks, clears supervision and removes projects from publication/review. Publication must be requested and reviewed again after access is restored. Both operations revoke existing parent unlock sessions. Local tests cover stale review, successful audit, duplicate rejection and suspension cleanup; live concurrent administrator/Auth changes still require validation. Deploy migration 011 with the updated admin page and API.

Migration 012 adds guardian consent withdrawal. Parent controls require a fresh verified parent session and an explicit confirmation before the service-only procedure clears consent and supervision, revokes unlock sessions, unpublishes projects and records an audit event in one transaction. Suspended accounts remain suspended; other accounts become pending. The UI clears locally displayed history after success. Existing project data, history and credit balances remain; this is not erasure or cancellation/refund of provider requests already in flight. Previously viewed pages and sent messages cannot be recalled. Re-entry requires a new consent/admin review and new publication review.

Local fixtures verify access/publication revocation, revision change, credit/project preservation and suspension preservation. The fresh OTP-to-withdrawal browser flow still requires configured Supabase acceptance.

Parent controls now receive the unlock expiry and clear displayed history, rule text and confirmation state when it expires. Focus/visibility events also check expiry after a background-tab delay. A server 401/403 clears those fields immediately. This is display hygiene in addition to server authorization, not a way to erase copies already seen. `npm run test:parent-browser` exercises expiry and server rejection against the running loopback app with synthetic API responses in Chrome; no real guardian/OTP acceptance is implied. Requires the local app on port 3217 or STUDIO_TEST_URL pointing to another loopback origin.

Migration 015 makes final parent unlock atomic with profile changes. The server snapshots the safety revision before verifying the email code, verifies the returned identity/email, then creates the hashed session under the profile lock only if revision and verified email still match. The database sets the fifteen-minute expiry. A suspended guardian can still unlock to review/delete history, without restoring building or publication. Unit cases cover stale revisions, email mismatch, malformed hashes and expiry. An independent PostgreSQL race confirms consent withdrawal defeats an in-flight unlock. Real Supabase OTP integration remains unverified.

Migration 016 adds independent per-account limits: three parent email-code sends and ten verification attempts in each fifteen-minute window. Slots are consumed before provider calls and are not refunded on errors or successful verification. PostgreSQL serializes competing attempts. Only two reusable rows per profile are retained, containing counters and window timestamps, not email or codes; profile deletion cascades. A missing limiter fails closed with 503, exhausted limits return 429. Provider-native and deployment-wide controls remain necessary; this does not limit sign-in attempts outside the parent endpoints.

## Atomic parent session start and rule changes

Migration 025 introduces service-only `studio_parent_control`. The parent API passes the hash of its HTTP-only unlock cookie (never returned in JSON). The database locks the profile and matching parent session, then checks expiry using wall-clock time after any lock wait. Starting supervision additionally requires current approved status, verified email and consent; duration comes from the database clock and is capped at 30 minutes. Updating family rules enforces at most ten nonempty strings of at most 400 characters and pauses supervision. Existing deletion holds remain effective.

This closes the gap between the initial HTTP parent check and these two mutations. Revocation that acquires the account lock first prevents a waiting session start. Requests committed before revocation remain ordered before it. Local SQL tests cover valid use, expired/missing/wrong tokens, malformed rules, missing consent and browser-role denial; a separate-connection PostgreSQL fixture verifies revocation wins against a waiting start. This does not claim every parent endpoint has been converted to this transaction, nor live Supabase OTP acceptance. Schema revision 25 is required; no live migration was applied.

Migration 026 extends the locked parent-control procedure to clear-history, withdraw-consent and request-deletion. Existing API confirmations remain required for consent withdrawal and deletion requests. All three operations now recheck the cookie-bound session after account/session locks; unexpected rule payloads are refused. The existing withdrawal/deletion procedures run inside that same transaction and invalidate unlocks. Clearing history deletes only rows belonging to the verified family. Pause remains available to the account without parent unlock, as a stop-access action. Notification retry and parent read responses are not covered by this mutation change.

New synthetic tests cover missing/revoked authority, payload rejection, other-family history isolation and unlock invalidation. The independent-connection race checks that a waiting history deletion rejects after unlock revocation and leaves the history intact. Schema revision 26 is required; no real history was deleted and no live migration was applied.

Migration 027 adds `studio_parent_mail_claim` for manual safety-alert retries. It locks the profile and cookie-bound parent session, checks wall-clock expiry and alert ownership, then calls the existing durable claim in the same transaction. The parent route passes its verified cookie hash through recipient lookup to both normal and unverified-recipient claim paths. Automatic safety notifications and scheduled workers continue using the original service claim; they do not depend on an interactive parent unlock. A notification leased before revocation can still be submitted and cannot be recalled.

Synthetic tests verify missing/expired authority, unavailable alerts, duplicate lease denial and independent automatic claiming. The separate-connection race proves revocation before a waiting manual claim creates no mail job. No provider request or real email is sent by these checks. Schema27 is required; no live migration applied.
